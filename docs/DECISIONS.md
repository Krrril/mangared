## 2026-07-26 — Название проекта: MangaRed (не MangaVerse)

Черновой мастер-план и первые прототипы называли проект "MangaVerse".
Финальное название — **MangaRed**.

*Почему*: выбор пользователя. Требует замены во всех местах: логотип,
UI-тексты ("MangaVerse Premium" → "MangaRed Premium" и т.д.), названия
пакетов/репозитория.

## 2026-07-26 — Память проекта: 5 файлов в /docs вместо 30-главной спецификации

Изначальный документ-концепт (`MangaVerse_Master_Plan.docx`) описывает
амбицию на 30 глав подробной спецификации (Vision, PRD, SRS, UI/UX Bible,
Database, Backend, Admin Panel, AI, Recommendation System, Security,
Roadmap и т.д.) — по сути, полноценную техническую книгу, достаточно
подробную, чтобы Claude/ChatGPT могли писать проект по ней почти
автоматически.

*Решение*: не писать 30 глав до старта кода. Вместо этого — 5 живых
файлов (`PROJECT.md`, `DESIGN_SYSTEM.md`, `ARCHITECTURE.md`,
`DECISIONS.md`, `ROADMAP.md`), которые перечитываются в начале каждой
сессии и обновляются по ходу работы.

*Почему*: 30 глав спецификации, написанные до единой строчки кода,
почти гарантированно разойдутся с тем, что реально понадобится — а
переписывать спеку дороже, чем менять 5 живых файлов. MVP из
[PROJECT.md](PROJECT.md) — это горизонт в несколько экранов, не в 30 тем.
Амбиции из мастер-плана никуда не делись — они разложены по фазам в
[ROADMAP.md](ROADMAP.md) и будут дораскрываться отдельными разделами
по мере того, как до них доходит очередь (например, полноценный
`docs/backend/`, `docs/admin/` и т.п. — когда эти фазы начнутся
по-настоящему).

*Отклонили*: писать все 30 глав сразу как "техническое задание для ИИ".

## 2026-07-26 — Дизайн-система восстановлена по скриншотам, не по исходникам

Скриншоты (веб и мобильная версии) приложены как изображения в чате, не
как файлы Figma/PNG на диске. Цвета в [DESIGN_SYSTEM.md](DESIGN_SYSTEM.md)
сняты на глаз, hover/active-состояния во многом додуманы по стандартной
практике (на статичном скриншоте их не видно).

*Почему это ок для старта*: цветовая палитра — это CSS-переменные в одном
месте (`src/styles`), поменять значения позже — минуты, а не переписывание
компонентов.

*Что сделать, если появятся исходники*: сверить хексы пипеткой и
поправить только раздел 1 в DESIGN_SYSTEM.md.

## 2026-07-26 — Стек: предложен Vite + React (SPA), не Next.js — статус: ждёт подтверждения

См. обоснование в [ARCHITECTURE.md](ARCHITECTURE.md). Кратко: пользователь
не работал с React/бэкендом раньше, SEO для каталога на MVP не критичен
(контента реального ещё нет), Next.js добавляет концепции (SSR/RSC),
которые не нужны для сквозного MVP.

*Статус*: **подтверждено пользователем**. Уточнение от пользователя: в
будущем понадобится подключить парсинг источников контента — это не
влияет на выбор фронтенд-стека, но означает, что позже появится отдельный
backend-сервис, отвечающий за парсинг/сбор данных (см. ARCHITECTURE.md,
раздел про будущий backend). Итоговый выбор: **Vite + React**.

## 2026-07-26 — Источник контента манги: открытый вопрос, не блокирует MVP

Пользователь попросил обсудить легальные варианты, а не сразу выбирать.
Рассмотренные варианты (см. обсуждение в чате):

1. **MangaDex API** — открытый бесплатный API, используется легальными
   клиентами (Tachiyomi/Mihon, Suwayomi). Технически открыт для сторонних
   приложений, но статус авторских прав на сканлейты внутри — спорный.
2. **Официальные лицензированные API** (аналог MANGA Plus, INKR,
   Comikey) — чисто легально, но требует партнёрств с правообладателями,
   нереалистично для MVP.
3. **Собственная площадка для авторов** (модель Webtoon Canvas/Tapas) —
   юридически самый чистый путь, хорошо сочетается с идеей админ-панели
   и монетизации из мастер-плана, но требует авторских кабинетов и
   модерации — отдельный большой кусок продукта.
4. **Парсинг произвольных сторонних сайтов без разрешения** — отклонено:
   нарушение ToS и авторских прав, такой скрейпинг не реализуется.

*Решение*: не блокирует MVP — MVP работает на моках через адаптер
контента (см. ARCHITECTURE.md) независимо от того, какой источник
выберем. Возврат к вопросу — при переходе к v2 (см. ROADMAP.md).

## 2026-07-26 — Источник контента: MangaDex API (обновляет решение выше)

Выбран **MangaDex** как источник реальных данных для MVP — вариант 1 из
предыдущей записи.

*Почему*: единственный из рассмотренных вариантов, который даёт рабочий
каталог с реальной мангой прямо сейчас, бесплатно, без переговоров с
правообладателями и без необходимости строить собственную площадку
авторов. Технически удобен для браузерного SPA: открытый CORS (проверено
живым запросом с `localhost`), не нужен свой бэкенд-прокси даже на
старте. Статус авторских прав на сканлейты внутри MangaDex действительно
спорный (см. предыдущую запись) — это принятый на MVP компромисс, не
финальное решение на все времена (см. "Открытый вопрос" ниже).

*Что это означает технически* (детали — в ARCHITECTURE.md, раздел
"Источник контента: MangaDex API"):
- Ничего не храним и не скачиваем сами — ни обложки, ни страницы. Только
  прямые ссылки на серверы MangaDex, запрашиваемые на лету.
- У части тайтлов главы лицензированы и физически не хранятся на
  MangaDex (только `externalUrl` на сайт правообладателя) — обнаружено
  вживую при проверке API (например, у Solo Leveling почти все главы —
  внешние). Наша читалка не может открыть такие главы. Решение
  пользователя: показывать такую главу в списке с кнопкой "Читать на
  сайте" вместо скрытия.

*Ограничения, с которыми придётся жить*:
- **Нет рекламы и платных сервисов поверх контента MangaDex** — это
  прямое требование их правил использования API, а не наше решение. У
  нас уже свёрстана карточка "MangaRed Premium" в сайдбаре — по решению
  пользователя она остаётся нерабочим визуальным макетом, реальная
  монетизация откладывается до отдельного решения (см. ROADMAP.md, v3).
  Вариант на будущее: если понадобится монетизация, для платной части
  может потребоваться другой источник контента (см. варианты 2–3 из
  предыдущей записи) параллельно с MangaDex для бесплатной части.
- **Обязательна атрибуция** MangaDex и групп сканлейта — сделано (см.
  ARCHITECTURE.md).

*Открытый вопрос на будущее*: MangaDex — решение для MVP и демонстрации
продукта, не обязательно финальный источник контента навсегда. Если
проект пойдёт дальше MVP, вопрос легального статуса контента стоит
пересмотреть отдельно (юридическая консультация вне компетенции этой
сессии).

## 2026-07-26 — Английский как второй полноценный язык, ещё 8 языков — рабочие заготовки

Интерфейс переведён на `ru` (полностью) и `en` (полностью). Ещё 8 языков
с экрана "Язык приложения" из мобильного макета (`kk`, `es`, `fr`, `de`,
`tr`, `ko`, `zh`, `ja`) добавлены как рабочие заготовки: короткие и
однозначные строки (пункты меню, кнопки, ярлыки) переведены, длинные
описательные тексты — нет отдельной пометки на "нужен перевод", кроме
общего указания здесь и в DESIGN_SYSTEM.md.

*Почему*: пользователь просил заготовки-ключи для остальных языков с
макета — короткие строки достаточно однозначны, чтобы перевести их
уверенно (это обычная лексика интерфейсов), в отличие от описаний
Premium-карточки и т.п., где нужен вкус носителя языка.

*Что сделать перед реальным запуском на этих языках*: отдать файлы
`src/i18n/locales/{kk,es,fr,de,tr,ko,zh,ja}.json` на вычитку носителю
языка или профессиональному переводчику — особенно длинные фразы.
Структура (ключи) у всех языков одинаковая, так что вычитка — это правка
значений, без изменения кода.

## 2026-07-26 — Библиотека/Избранное/История без аккаунтов: честный MVP-скоуп

Домучили оставшиеся пункты сайдбара (Категории, Топ манги, Библиотека,
Избранное, История, Обновления — все вели в заглушку или были
некликабельны). Для Библиотеки/Избранного/Истории решение: не имитировать
функции, которых на самом деле нет, а честно ограничиться тем, что
реально работает без бэкенда и аккаунтов.

*Что это значит*:
- **Библиотека** = список тайтлов с сохранённым прогрессом чтения
  ("Читаю сейчас"). На мобильном макете у Библиотеки несколько вкладок
  (Читаю / Планирую прочитать / Прочитано) — вкладки без бэкенда и
  пользовательских списков реализовать нечем, это в v2 (ROADMAP.md).
- **Избранное** — новый маленький сервис `src/services/favorites`,
  паттерн один в один с `services/progress` (localStorage, id тайтлов).
  Кнопка-сердце на странице тайтла теперь реально переключает состояние.
- **История** — это те же данные, что и "Продолжить чтение" на главной
  (прогресс из localStorage), просто без ограничения по количеству и на
  отдельной странице. Отдельного журнала "что когда открывали" нет —
  только "текущая позиция по каждому тайтлу", как и раньше.

*Почему так, а не заглушка*: заглушка "Скоро" была бы формально честнее
про будущее, но эти три раздела реально можно сделать полезными прямо
сейчас на localStorage — глупо изображать пустоту там, где есть
работающие данные (прогресс уже сохранялся и до этого, просто не было
экрана, чтобы это увидеть).

*Ограничение, которое стоит держать в голове*: все эти данные живут в
localStorage конкретного браузера — не переживут смену устройства и не
синхронизируются, пока не появится бэкенд с авторизацией (v2).

## 2026-07-27 — Переход на backend: Express + Prisma + PostgreSQL (не NestJS)

Реализован собственный backend (`server/`) для пользовательских данных
(аккаунты, избранное, прогресс чтения). Манга по-прежнему не хранится
нигде у нас — только в MangaDex API, backend её вообще не касается.

*Почему Express, а не NestJS*: та же логика, что и выбор Vite вместо
Next.js в начале проекта (см. запись выше про Vite) — пользователь
только начинает работать с backend, и NestJS добавил бы ещё один пласт
концепций (декораторы, DI, модули) поверх и так новых понятий (роуты,
middleware, ORM, JWT). Express — это просто функции-обработчики,
которые легче объяснить построчно. Подробное сравнение — в
ARCHITECTURE.md.

*Почему Prisma*: единая читаемая схема в одном файле
(`schema.prisma`), автогенерируемый TypeScript-клиент с автодополнением
по полям таблиц, миграции одной командой. Alternative — raw SQL/`pg`
даёт больше контроля, но заставляет вручную синхронизировать типы с
БД — лишняя забота для MVP.

*Почему PostgreSQL, а не что-то полегче (SQLite и т.п.)*: прямой запрос
пользователя ("подними backend с PostgreSQL"), плюс PostgreSQL —
разумный дефолт для проекта, который в будущем может дорасти до
реальных пользователей.

*Где развёрнута база*: локальный PostgreSQL 17, установлен через
`winget install PostgreSQL.PostgreSQL.17`. Тихая установка не сохранила
пароль администратора — пришлось сбрасывать стандартной процедурой
(временный `trust`-доступ + `ALTER USER ... PASSWORD` + возврат
`scram-sha-256`), это делалось руками пользователя в PowerShell с
правами администратора — Claude Code не может управлять службами
Windows без повышенных прав (та же история, что с правами на саму
папку проекта в начале работы).

## 2026-07-27 — JWT в localStorage вместо httpOnly-cookie

Аутентификация — email + пароль, пароль хешируется bcrypt (не хранится
в открытом виде), сервер выдаёт JWT на 30 дней, фронтенд кладёт его в
`localStorage` и шлёт в заголовке `Authorization: Bearer`.

*Компромисс, принятый осознанно*: токен в localStorage доступен любому
JS на странице — при XSS-атаке его можно украсть. `httpOnly`-cookie
безопаснее (обычный JS её не видит), но требует больше инфраструктуры
(CORS с credentials, защита от CSRF) — решено не удваивать сложность в
момент первого знакомства с аутентификацией.

*Когда пересмотреть*: до того, как в проекте появятся настоящие платящие
пользователи или чувствительные данные — тогда переход на httpOnly-cookie
стоит сделать одним из первых пунктов security-подготовки (см.
ROADMAP.md, v3).

## 2026-07-27 — Прогресс чтения хранит номер страницы, не процент

Схема БД, которую задал пользователь, хранит `pageNumber` (номер
страницы), не процент прочитанного. Раньше (localStorage-версия)
хранился именно процент, посчитанный в читалке в момент сохранения
(`pageIndex / totalPages`).

*Почему не оставили процент*: посчитать его на бэкенде или при простом
чтении списка (Библиотека, История) невозможно без знания общего числа
страниц в главе — а общее число страниц мы нигде не храним (это данные
MangaDex, дублировать их у себя — нарушение принципа "ничего не храним
сами", см. ARCHITECTURE.md). Решение: везде, где раньше показывался
процент с прогресс-баром, теперь текст "Глава N · стр. M" — честно
показывает то, что реально знаем.

*Что изменилось в коде*: `ReadingProgress.percent` → `ReadingProgress.pageNumber`
(`src/services/content/types.ts`), `ContinueReadingRow` больше не рисует
`ProgressBar` (компонент удалён как неиспользуемый).

## 2026-07-27 — Гостевой режим: localStorage остаётся, не только для перехода

Избранное и прогресс чтения теперь идут в PostgreSQL **только если
пользователь авторизован** — иначе, как и раньше, в localStorage
браузера. Это не временный костыль на время миграции, а осознанное
постоянное поведение: регистрация не обязательна, чтобы пользоваться
MangaRed.

*Как это устроено технически*: `src/services/favorites` и
`src/services/progress` сами проверяют, есть ли сохранённый токен
(`getStoredToken()`), и решают, куда обращаться — компоненты вызывают
одни и те же функции независимо от режима. Из-за этого все функции этих
сервисов стали асинхронными (`Promise`), даже для гостя — единый
контракт проще поддерживать, чем два разных API.

*Известное ограничение*: данные гостя и данные аккаунта — независимы.
Если гость зарегистрируется, его localStorage-избранное/прогресс
автоматически в базу не переносятся. Перенос гостевых данных при первой
регистрации — в бэклог (см. ROADMAP.md).

## 2026-07-27 — Имя пользователя + вход через Google, Apple отложен

По просьбе пользователя регистрация расширена полем "Имя" (отдельно от
email — email остаётся логином/идентификатором, имя — то, что видно в
интерфейсе, например в Topbar вместо email). Добавлен вход через Google.

*Почему Google, а не полный список "как в макете"*: пользователь просил
"войти через iOS/Google и какие ещё есть" — Google Identity Services
бесплатен и настраивается за 5 минут (только Client ID, без секретов и
без похода за одобрением к Google). Реализовано полностью — см.
ARCHITECTURE.md, "Вход через Google".

*Почему Apple — только неактивная кнопка "скоро"*: "Sign in with Apple"
требует платного членства в Apple Developer Program (99$/год) — плата
только за возможность НАСТРОИТЬ вход, ещё до какой-либо реальной пользы
от приложения. Несоразмерно для тестирования MVP. Кнопка на месте (не
спрятана — честно показывает, что опция существует и появится), при
клике ничего не происходит, есть подсказка почему.

*Схема БД*: `passwordHash` стал опциональным (`String?`) — у
пользователей, вошедших только через Google, пароля физически нет,
хешировать нечего. Добавлено поле `googleId` (уникальное, опциональное)
для связи с аккаунтом Google. Если email уже был зарегистрирован через
пароль, а потом тот же человек входит через Google с тем же email —
аккаунты не дублируются, `googleId` просто привязывается к
существующей записи.

## 2026-07-27 — Перенос гостевых данных при входе/регистрации, приоритет у БД

Реализован автоматический перенос localStorage (избранное + прогресс) в
аккаунт при первом успешном входе/регистрации/входе через Google — новый
модуль `src/services/migration`, вызывается из `AuthContext` сразу после
получения токена, до того как компоненты успеют что-то прочитать под
новой авторизацией.

*Логика слияния*:
- **Избранное** — просто объединяем оба множества: каждый локальный
  `mangaId` отправляется на `POST /api/favorites`, бэкенд делает upsert
  (уникальный индекс `(userId, mangaId)`), так что дубли и повторный
  вызов ничего не портят.
- **Прогресс** — тут настоящий конфликт возможен (одна запись на тайтл),
  поэтому сначала запрашиваем текущий прогресс из БД и переносим только
  те тайтлы, которых там **ещё нет**. Если пользователь уже читал этот
  тайтл на другом устройстве — его прогресс в БД остаётся как есть,
  гостевые данные с этого браузера для этого тайтла отбрасываются.
- После успешного переноса — `localStorage` очищается (иначе при
  следующем визите без входа гость увидит собственные старые данные как
  будто ничего не изменилось).

*Почему БД побеждает, а не "последний вход"*: гостевые данные с
конкретного браузера почти всегда менее ценны, чем то, что уже
накоплено на аккаунте (могло быть с другого, "основного" устройства) —
безопаснее не потерять существующий прогресс, чем гнаться за
актуальностью. Если это когда-нибудь станет проблемой (пользователь
жалуется, что не видит недавнего гостевого прогресса) — можно перейти
на сравнение по `updatedAt`, но это усложнение отложено до реального
запроса.

*Если перенос не удался* (бэкенд недоступен, сеть) — `localStorage` не
чистится: гостевые данные остаются на месте, следующий вход попробует
перенести их снова. Ошибка логируется в консоль, но не блокирует и не
показывается пользователю — вход всё равно должен состояться.

*Проверено вживую*: гость добавил 2 тайтла в избранное и прочитал
2 главы → зарегистрировался → всё нашлось в PostgreSQL. Затем отдельно
проверен конфликтный сценарий: тот же пользователь как гость "прочитал"
(искусственно, через localStorage) тот же тайтл на другой странице плюс
новый тайтл, которого не было в БД → вошёл повторно → запись в БД для
существующего тайтла осталась нетронутой, новый тайтл добавился,
дублей в избранном не возникло.

## MangaDex-запросы переведены на прокси через backend (2026-07-29)

После первого реального деплоя на Vercel сайт открывался, но все секции
с мангой были пустыми. В консоли браузера — ошибка CORS: MangaDex
отвечал 200, но без заголовка `Access-Control-Allow-Origin` для домена
`*.vercel.app`. Прямая проверка `https://api.mangadex.org/manga?limit=1`
в адресной строке показывала нормальный JSON — то есть сам API жив,
проблема именно в CORS-заголовках для конкретного домена/типа запроса.
Локально (на `localhost:5173`) прямые запросы работали всегда, поэтому
проблема не была видна раньше — всплыла только на реальном хостинге.

**Решение**: все JSON-запросы к MangaDex (`mdFetch` в
`src/api/mangadex/client.ts`) теперь идут не напрямую из браузера, а
через прокси-роут на своём backend — `GET /api/mangadex/*`
(`server/src/routes/mangadex.ts`), который просто пересылает путь и
query-параметры на `api.mangadex.org` и отдаёт ответ как есть. Запрос
сервер→сервер CORS не касается вообще (это ограничение браузера), так
что проблема решается полностью, независимо от того, почему именно
MangaDex блокирует конкретный домен.

Это отменяет более раннее решение "прокси не нужен" (см. выше, раздел
"Источник контента: MangaDex API") — тогда оно было верным для
локальной разработки, но не учитывало поведение MangaDex на реальном
домене. Обложки и страницы глав прокси не требуют — они грузятся через
`<img src>`, а не `fetch()`, и CORS на них не распространяется.

## Обложки/страницы MangaDex грузятся с `referrerPolicy="no-referrer"` (2026-07-29)

После фикса прокси для JSON-запросов (см. запись выше) секции на проде
заполнились текстом (названия, рейтинги, главы), но вместо обложек
показывались одинаковые заглушки "You can read this at: MANGADEX" —
Chrome DevTools показывали `naturalWidth: 600, naturalHeight: 642`
(нетипичные для обложки пропорции) для картинок с разных тайтлов —
подозрительно одинаковый размер для разного контента.

*Диагностика*: прямой переход по ссылке на обложку в адресной строке —
показывает настоящую картинку. Тот же URL, загруженный через `<img>` со
страницы `mangared-theta.vercel.app` — заглушка. Разница — только в
заголовке `Referer`, который браузер сам добавляет к запросам с
реального сайта, но не добавляет при прямом переходе. Проверено
напрямую через `new Image()` с `referrerPolicy: 'no-referrer'` —
возвращает настоящую обложку (256×402, разумные пропорции книги)
против `600×642` с обычной политикой.

**Вывод**: у MangaDex есть защита от хотлинков (hotlink protection) по
`Referer` — сторонний сайт получает вместо изображения брендированную
заглушку. Раньше в локальной разработке этого не было видно — возможно,
у `localhost` какое-то особое исключение, либо защита появилась
недавно.

**Решение**: на все `<img>`, которые грузят обложки/страницы глав с
MangaDex (`CoverPlaceholder.tsx`, `HeroBanner.tsx`, `Reader.tsx`)
добавлен атрибут `referrerPolicy="no-referrer"` — браузер не отправляет
заголовок `Referer` вовсе, MangaDex не видит, с какого сайта пришёл
запрос, и отдаёт настоящую картинку. JSON-прокси через backend это не
затрагивает (уже сделан отдельно), только `<img>`.

## Регистрация/вход падали на проде: миграция БД не догоняла schema.prisma (2026-07-29)

При живой проверке регистрации на Vercel/Render — `/api/auth/register` и
`/api/auth/login` возвращали 502, причём backend уходил в краш-луп (падал
и перезапускался). В логах Render — `PrismaClientKnownRequestError`:
`The column users.name does not exist in the current database` (код
P2022). Любой запрос через Prisma, трогающий модель `User`, кидал
необработанное исключение (`findUnique` уже падает на SELECT) — в Node
18+/20+/22+ необработанный `unhandledRejection` по умолчанию завершает
процесс, поэтому сервис не просто отдавал 500, а полностью падал.

**Причина**: поля `name` (2026-07-27, см. запись "Имя пользователя +
вход через Google") и `googleId`, а также снятие `NOT NULL` с
`password_hash`, были добавлены в `schema.prisma` и применены к
**локальной** dev-базе через `prisma db push` — быстрый способ синхронизировать
схему без создания файла миграции (см. более раннюю запись про
`db push --accept-data-loss` как dev-only приём). Из-за этого в
`server/prisma/migrations/` остался только самый первый `init`,
без этих изменений — а `prisma migrate deploy` в `render.yaml`
(команда сборки на Render) применяет только то, что реально лежит в
папке миграций. Реальная база на Render создавалась с нуля через
Blueprint и получила только `init` — без `name`/`google_id`/nullable
`password_hash`.

**Решение**: вручную написана недостающая миграция
`server/prisma/migrations/20260729193500_add_name_and_google_auth/migration.sql`
(добавляет `name` NOT NULL, `google_id` UNIQUE nullable, снимает NOT NULL
с `password_hash`). Проверена на одноразовой пустой локальной базе —
`prisma migrate deploy` применяет обе миграции по порядку без ошибок,
`prisma.user.create`/`findUnique` работают. После пуша Render применит
её при следующем деплое (та же команда сборки, `prisma migrate deploy`).

**Урок на будущее**: `prisma db push` для локальной разработки — ок для
скорости, но каждое изменение `schema.prisma`, которое в итоге попадает
в `main`, должно сопровождаться настоящим файлом миграции (`prisma
migrate dev --name ...` вместо `db push`, либо миграция дописывается
руками, как в этот раз) — иначе прод после первого же деплоя с нуля
получит структуру БД, не совпадающую со схемой, и упадёт именно так, как
описано выше. Стоит завести привычку: перед пушем в `main` проверять
`npx prisma migrate status` (или мысленно — "есть ли файл миграции под
каждое изменение schema.prisma с прошлого коммита").
