# DECISIONS.md — журнал решений MangaRed

Формат записи: **Дата — Решение**, затем *Почему* и *Альтернативы,
которые отклонили*. Новые записи добавляются в конец. Ничего не удаляем —
если решение отменено, добавляем новую запись, которая на это ссылается.

---

## 2026-07-26 — Название проекта: MangaRed (не MangaVerse)

Черновой мастер-план и первые прототипы называли проект "MangaVerse".
Финальное название — **MangaRed**.

*Почему*: выбор пользователя. Требует замены во всех местах: логотип,
UI-тексты ("MangaVerse Premium" → "MangaRed Premium" и т.д.), названия
пакетов/репозитория.

## 2026-07-26 — Память проекта: 5 файлов в /docs вместо 30-главной спецификации

Изначальный документ-концепт (`MangaVerse_Master_Plan.docx`) описывает
амбицию на 30 глав подробной спецификации (Vision, PRD, SRS, UI/UX Bible,
Database, Backend, Admin Panel, AI, Recommendation System, Security,
Roadmap и т.д.) — по сути, полноценную техническую книгу, достаточно
подробную, чтобы Claude/ChatGPT могли писать проект по ней почти
автоматически.

*Решение*: не писать 30 глав до старта кода. Вместо этого — 5 живых
файлов (`PROJECT.md`, `DESIGN_SYSTEM.md`, `ARCHITECTURE.md`,
`DECISIONS.md`, `ROADMAP.md`), которые перечитываются в начале каждой
сессии и обновляются по ходу работы.

*Почему*: 30 глав спецификации, написанные до единой строчки кода,
почти гарантированно разойдутся с тем, что реально понадобится — а
переписывать спеку дороже, чем менять 5 живых файлов. MVP из
[PROJECT.md](PROJECT.md) — это горизонт в несколько экранов, не в 30 тем.
Амбиции из мастер-плана никуда не делись — они разложены по фазам в
[ROADMAP.md](ROADMAP.md) и будут дораскрываться отдельными разделами
по мере того, как до них доходит очередь (например, полноценный
`docs/backend/`, `docs/admin/` и т.п. — когда эти фазы начнутся
по-настоящему).

*Отклонили*: писать все 30 глав сразу как "техническое задание для ИИ".

## 2026-07-26 — Дизайн-система восстановлена по скриншотам, не по исходникам

Скриншоты (веб и мобильная версии) приложены как изображения в чате, не
как файлы Figma/PNG на диске. Цвета в [DESIGN_SYSTEM.md](DESIGN_SYSTEM.md)
сняты на глаз, hover/active-состояния во многом додуманы по стандартной
практике (на статичном скриншоте их не видно).

*Почему это ок для старта*: цветовая палитра — это CSS-переменные в одном
месте (`src/styles`), поменять значения позже — минуты, а не переписывание
компонентов.

*Что сделать, если появятся исходники*: сверить хексы пипеткой и
поправить только раздел 1 в DESIGN_SYSTEM.md.

## 2026-07-26 — Стек: предложен Vite + React (SPA), не Next.js — статус: ждёт подтверждения

См. обоснование в [ARCHITECTURE.md](ARCHITECTURE.md). Кратко: пользователь
не работал с React/бэкендом раньше, SEO для каталога на MVP не критичен
(контента реального ещё нет), Next.js добавляет концепции (SSR/RSC),
которые не нужны для сквозного MVP.

*Статус*: **подтверждено пользователем**. Уточнение от пользователя: в
будущем понадобится подключить парсинг источников контента — это не
влияет на выбор фронтенд-стека, но означает, что позже появится отдельный
backend-сервис, отвечающий за парсинг/сбор данных (см. ARCHITECTURE.md,
раздел про будущий backend). Итоговый выбор: **Vite + React**.

## 2026-07-26 — Авторизация: не в MVP, добавляется в v2

*Почему*: MVP работает с одним локальным "пользователем" без логина,
прогресс чтения — в localStorage. Экраны логина/регистрации и привязка
данных к аккаунту — в v2, вместе с реальным бэкендом и синхронизацией.
Это решение пользователя (выбрано как рекомендованный вариант).

## 2026-07-26 — i18n закладывается в архитектуру сразу, с одним языком (RU)

*Почему*: на скриншотах есть экран выбора языка (10+ языков) — значит
мультиязычность запланирована продуктово. Дешевле сразу прогонять все
тексты через `react-i18next` (даже заполнив только `ru`), чем потом
вычищать хардкод-строки из всех компонентов. Стоимость на старте
минимальна — один словарь вместо инлайн-строк. Это решение пользователя
(выбран рекомендованный вариант).

## 2026-07-26 — Источник контента манги: открытый вопрос, не блокирует MVP

Пользователь попросил обсудить легальные варианты, а не сразу выбирать.
Рассмотренные варианты (см. обсуждение в чате):

1. **MangaDex API** — открытый бесплатный API, используется легальными
   клиентами (Tachiyomi/Mihon, Suwayomi). Технически открыт для сторонних
   приложений, но статус авторских прав на сканлейты внутри — спорный.
2. **Официальные лицензированные API** (аналог MANGA Plus, INKR,
   Comikey) — чисто легально, но требует партнёрств с правообладателями,
   нереалистично для MVP.
3. **Собственная площадка для авторов** (модель Webtoon Canvas/Tapas) —
   юридически самый чистый путь, хорошо сочетается с идеей админ-панели
   и монетизации из мастер-плана, но требует авторских кабинетов и
   модерации — отдельный большой кусок продукта.
4. **Парсинг произвольных сторонних сайтов без разрешения** — отклонено:
   нарушение ToS и авторских прав, такой скрейпинг не реализуется.

*Решение*: не блокирует MVP — MVP работает на моках через адаптер
контента (см. ARCHITECTURE.md) независимо от того, какой источник
выберем. Возврат к вопросу — при переходе к v2 (см. ROADMAP.md).

## 2026-07-26 — Источник контента: MangaDex API (обновляет решение выше)

Выбран **MangaDex** как источник реальных данных для MVP — вариант 1 из
предыдущей записи.

*Почему*: единственный из рассмотренных вариантов, который даёт рабочий
каталог с реальной мангой прямо сейчас, бесплатно, без переговоров с
правообладателями и без необходимости строить собственную площадку
авторов. Технически удобен для браузерного SPA: открытый CORS (проверено
живым запросом с `localhost`), не нужен свой бэкенд-прокси даже на
старте. Статус авторских прав на сканлейты внутри MangaDex действительно
спорный (см. предыдущую запись) — это принятый на MVP компромисс, не
финальное решение на все времена (см. "Открытый вопрос" ниже).

*Что это означает технически* (детали — в ARCHITECTURE.md, раздел
"Источник контента: MangaDex API"):
- Ничего не храним и не скачиваем сами — ни обложки, ни страницы. Только
  прямые ссылки на серверы MangaDex, запрашиваемые на лету.
- У части тайтлов главы лицензированы и физически не хранятся на
  MangaDex (только `externalUrl` на сайт правообладателя) — обнаружено
  вживую при проверке API (например, у Solo Leveling почти все главы —
  внешние). Наша читалка не может открыть такие главы. Решение
  пользователя: показывать такую главу в списке с кнопкой "Читать на
  сайте" вместо скрытия.

*Ограничения, с которыми придётся жить*:
- **Нет рекламы и платных сервисов поверх контента MangaDex** — это
  прямое требование их правил использования API, а не наше решение. У
  нас уже свёрстана карточка "MangaRed Premium" в сайдбаре — по решению
  пользователя она остаётся нерабочим визуальным макетом, реальная
  монетизация откладывается до отдельного решения (см. ROADMAP.md, v3).
  Вариант на будущее: если понадобится монетизация, для платной части
  может потребоваться другой источник контента (см. варианты 2–3 из
  предыдущей записи) параллельно с MangaDex для бесплатной части.
- **Обязательна атрибуция** MangaDex и групп сканлейта — сделано (см.
  ARCHITECTURE.md).

*Открытый вопрос на будущее*: MangaDex — решение для MVP и демонстрации
продукта, не обязательно финальный источник контента навсегда. Если
проект пойдёт дальше MVP, вопрос легального статуса контента стоит
пересмотреть отдельно (юридическая консультация вне компетенции этой
сессии).

## 2026-07-26 — Английский как второй полноценный язык, ещё 8 языков — рабочие заготовки

Интерфейс переведён на `ru` (полностью) и `en` (полностью). Ещё 8 языков
с экрана "Язык приложения" из мобильного макета (`kk`, `es`, `fr`, `de`,
`tr`, `ko`, `zh`, `ja`) добавлены как рабочие заготовки: короткие и
однозначные строки (пункты меню, кнопки, ярлыки) переведены, длинные
описательные тексты — нет отдельной пометки на "нужен перевод", кроме
общего указания здесь и в DESIGN_SYSTEM.md.

*Почему*: пользователь просил заготовки-ключи для остальных языков с
макета — короткие строки достаточно однозначны, чтобы перевести их
уверенно (это обычная лексика интерфейсов), в отличие от описаний
Premium-карточки и т.п., где нужен вкус носителя языка.

*Что сделать перед реальным запуском на этих языках*: отдать файлы
`src/i18n/locales/{kk,es,fr,de,tr,ko,zh,ja}.json` на вычитку носителю
языка или профессиональному переводчику — особенно длинные фразы.
Структура (ключи) у всех языков одинаковая, так что вычитка — это правка
значений, без изменения кода.

## 2026-07-26 — Библиотека/Избранное/История без аккаунтов: честный MVP-скоуп

Домучили оставшиеся пункты сайдбара (Категории, Топ манги, Библиотека,
Избранное, История, Обновления — все вели в заглушку или были
некликабельны). Для Библиотеки/Избранного/Истории решение: не имитировать
функции, которых на самом деле нет, а честно ограничиться тем, что
реально работает без бэкенда и аккаунтов.

*Что это значит*:
- **Библиотека** = список тайтлов с сохранённым прогрессом чтения
  ("Читаю сейчас"). На мобильном макете у Библиотеки несколько вкладок
  (Читаю / Планирую прочитать / Прочитано) — вкладки без бэкенда и
  пользовательских списков реализовать нечем, это в v2 (ROADMAP.md).
- **Избранное** — новый маленький сервис `src/services/favorites`,
  паттерн один в один с `services/progress` (localStorage, id тайтлов).
  Кнопка-сердце на странице тайтла теперь реально переключает состояние.
- **История** — это те же данные, что и "Продолжить чтение" на главной
  (прогресс из localStorage), просто без ограничения по количеству и на
  отдельной странице. Отдельного журнала "что когда открывали" нет —
  только "текущая позиция по каждому тайтлу", как и раньше.

*Почему так, а не заглушка*: заглушка "Скоро" была бы формально честнее
про будущее, но эти три раздела реально можно сделать полезными прямо
сейчас на localStorage — глупо изображать пустоту там, где есть
работающие данные (прогресс уже сохранялся и до этого, просто не было
экрана, чтобы это увидеть).

*Ограничение, которое стоит держать в голове*: все эти данные живут в
localStorage конкретного браузера — не переживут смену устройства и не
синхронизируются, пока не появится бэкенд с авторизацией (v2).
