## Стек

### Frontend: React + Vite (не Next.js)

| Критерий | Vite + React (SPA) | Next.js |
|---|---|---|
| Порог входа | Ниже — обычный React, без концепций SSR/RSC/route handlers поверх | Выше — нужно сразу понимать серверный рендеринг |
| Скорость разработки/HMR | Очень быстрый dev-сервер | Быстрый, но тяжелее Vite |
| SEO / серверный рендеринг | Нет из коробки (не критично для MVP — каталог за моками, не индексируется) | Из коробки |
| Backend "из коробки" (API routes) | Нет — бэкенд отдельно | Есть — но у нас пока backend не с самого начала (моки) |
| Перенос логики в React Native позже | Проще — SPA-код (хуки, стейт, сервисные слои) переносится почти как есть | Next-специфичный роутинг/данные придётся распутывать |

**Почему Vite для MVP**: пользователь не работал с React и бэкендом раньше —
важно не смешивать в один момент "учу React" и "учу серверный рендеринг
Next.js". Vite даёт чистый, предсказуемый React без магии, быстрый цикл
разработки, и ничего не потеряется — если позже понадобится SEO для
публичного каталога, миграция на Next.js делается инкрементально, так как
UI-компоненты и стейт-логика останутся почти без изменений.

**Когда стоит пересмотреть**: если приоритетом станет публичная
индексация каталога в поиске (SEO — глава 28 из исходного мастер-плана)
раньше, чем ожидается — тогда переезд на Next.js стоит сделать раньше, а
не после того как накопится много страниц.

### Остальной стек (для MVP)

| Слой | Выбор | Почему |
|---|---|---|
| Роутинг | `react-router` | Стандарт для SPA на Vite |
| Стили | CSS Modules + CSS-переменные из DESIGN_SYSTEM.md | Знакомо (вы верстаете на CSS), не требует изучать CSS-in-JS с нуля; переменные = единый источник правды для темы |
| Иконки | `lucide-react` | Соответствует стилю референсов (см. DESIGN_SYSTEM.md) |
| Состояние | React Context + хуки (без Redux/Zustand на старте) | На MVP состояния немного (прогресс чтения, тема); лишняя библиотека — лишняя концепция для изучения. Пересмотрим, если состояние разрастётся |
| Данные о манге | MangaDex API напрямую из браузера, через "адаптер" (см. ниже) | Своих данных о манге как не было, так и нет — см. "Источник контента" ниже |
| Данные пользователя (избранное, прогресс) | Свой backend + PostgreSQL, с фолбэком на localStorage для гостей | См. раздел "Backend и база данных" ниже |
| i18n | `react-i18next`, с самого начала, даже с одним языком (ru) | Продуктово запланирована мультиязычность (см. селектор языка на референсах); дешевле сразу прогонять тексты через словарь, чем потом вычищать хардкод |
| Аутентификация | Email + пароль, свой backend, JWT | См. раздел "Backend и база данных" ниже |

## Источник контента: MangaDex API

С 2026-07-26 источник реальных данных — открытый API
[MangaDex](https://api.mangadex.org/docs/) (см. обоснование выбора в
DECISIONS.md). Ключевой принцип: **мы ничего не храним и не скачиваем
сами** — ни обложки, ни страницы глав. Всё, что видит пользователь —
это прямые ссылки на серверы MangaDex, запрошенные "на лету":

- **Обложки** — `https://uploads.mangadex.org/covers/{mangaId}/{fileName}.256.jpg`
  (список) или `.512.jpg` (страница тайтла/баннер). Просто `<img src>`,
  никакого прокси или скачивания.
- **Страницы главы** — получаются через `/at-home/server/{chapterId}`
  **только в момент открытия читалки**, не заранее и не пакетно (это и
  требование MangaDex, и естественно ложится на "не храним сами").
  Ссылка вида `{baseUrl}/data/{hash}/{filename}` живёт достаточно долго
  для одного сеанса чтения, повторно не кэшируется на диске.
- **Метаданные** (название, описание, теги, рейтинг, список глав) —
  JSON-запросы к MangaDex. **С 2026-07-29 идут не напрямую из браузера, а
  через прокси на нашем backend** (`GET /api/mangadex/*` →
  `server/src/routes/mangadex.ts`, просто пересылает путь и query на
  `api.mangadex.org` и отдаёт ответ как есть) — раньше ходили напрямую
  (CORS был открыт), но на реальном домене (Vercel) MangaDex перестал
  отдавать `Access-Control-Allow-Origin` для наших запросов, хотя
  локально это работало. Причина на стороне MangaDex не выяснена
  (возможно, точечная блокировка домена/сети хостинга) — прокси решает
  проблему полностью, так как между сервером и MangaDex никакого CORS
  нет в принципе (это ограничение браузера, не серверов). Обложки и
  страницы глав по-прежнему грузятся напрямую (см. ниже) — они идут через
  `<img src>`, а не `fetch()`, поэтому CORS их не касается.

### Лицензированные ("внешние") главы

У многих популярных тайтлов часть или все главы лицензированы — сам
MangaDex не хранит их страницы, а отдаёт только `externalUrl` на сайт
правообладателя (Webnovel, Tappytoon и т.п.). Наша читалка **не может**
открыть такие главы напрямую. Обработка (решение пользователя,
2026-07-26): такие главы остаются в списке глав тайтла, но вместо
внутренней ссылки — кнопка "Читать на сайте", открывающая `externalUrl`
в новой вкладке (см. `TitlePage.tsx`, `ChapterRow`). Кнопка "Читать" на
странице тайтла ведёт на первую **не**-внешнюю главу.

### Ограничения MangaDex, которые важно держать в голове

- **Контент-рейтинг**: показываем только `safe` + `suggestive` (без
  эротики/порнографии) — см. `CONTENT_RATINGS` в `src/api/mangadex/constants.ts`.
- **Никакой рекламы и платных сервисов поверх контента из API** — прямое
  требование правил MangaDex. Конфликтует с уже свёрстанной карточкой
  "MangaGreen Premium" в сайдбаре — по решению пользователя (2026-07-26)
  она остаётся нерабочим макетом до отдельного решения по монетизации
  (см. ROADMAP.md, v3, и DECISIONS.md).
- **Обязательная атрибуция**: MangaDex и группы сканлейта нужно
  указывать в интерфейсе. Сделано: строка "Данные и главы предоставлены
  MangaDex" в подвале сайдбара, название группы перевода — в списке глав
  тайтла и в панели настроек читалки.
- **Язык контента ≠ язык интерфейса**: контент (главы) сейчас всегда
  запрашивается на английском (`CONTENT_LANGUAGE` в constants.ts) — это
  отдельная настройка от языка UI (см. src/i18n) и от MangaDex зависит,
  есть ли вообще перевод главы на нужный язык. Переключение языка
  контента — в бэклог (см. ROADMAP.md).
- **Список глав** загружается одним запросом (до 100 последних) без
  полной пагинации — для MVP достаточно, полная пагинация через
  `offset` — в бэклог.

## Backend и база данных

С 2026-07-27 у MangaGreen есть свой backend (`server/`) — но только для
**пользовательских** данных (аккаунты, избранное, прогресс чтения).
Сама манга по-прежнему не хранится нигде у нас — фронтенд как ходил в
MangaDex напрямую, так и ходит (см. "Источник контента" выше). Это два
независимых источника данных, которые просто оба используются в одном
приложении.

### Стек backend: Express + TypeScript + Prisma (не NestJS)

| Критерий | Express | NestJS |
|---|---|---|
| Порог входа | Ниже — обычные функции-обработчики, без декораторов/DI/модулей | Выше — Angular-стиль (декораторы, модули, провайдеры, guards) — ещё один пласт концепций поверх и так нового для вас backend-опыта |
| Гибкость | Минимум навязанной структуры, легко объяснить построчно | Много готовой архитектуры "из коробки" — полезно в большой команде, избыточно для одного разработчика на старте |
| Экосистема/документация | Огромная, часто самый первый пример, который находишь | Тоже большая, но многие туториалы уже подразумевают знакомство с Angular-паттернами |

**Почему Express** — та же логика, что и с выбором Vite вместо Next.js
(см. выше): вы только начинаете работать с backend, и не стоит сразу
учить фреймворк с собственной философией (DI, декораторы) поверх и так
новых понятий (роуты, middleware, ORM, JWT). Express — это просто
функции, которые получают запрос и отвечают; лишнего слоя абстракции
между вами и тем, что реально происходит, нет.

**ORM: Prisma**. Даёт схему в одном читаемом файле
(`server/prisma/schema.prisma`), автоматически сгенерированный
TypeScript-клиент (автодополнение по полям таблиц) и понятные миграции
одной командой. Alternative — писать чистый SQL или `pg` напрямую — даёт
больше контроля, но заставляет самостоятельно синхронизировать типы
TypeScript со схемой БД, что на старте лишняя головная боль.

### Схема базы данных

Три таблицы, ровно то, что нужно пользователю — сама манга (её ID,
названия, обложки, главы) в базу не попадает, только ссылки на неё:

```prisma
model User {
  id           String   @id @default(uuid())
  email        String   @unique
  name         String
  passwordHash String?  // bcrypt-хеш; null у пользователей, вошедших только через Google
  googleId     String?  @unique // id аккаунта Google, если вход был через него
  createdAt    DateTime @default(now())
}

model Favorite {
  id        String   @id @default(uuid())
  userId    String
  mangaId   String   // id тайтла на MangaDex — просто строка, без FK на несуществующую у нас таблицу
  createdAt DateTime @default(now())
  @@unique([userId, mangaId]) // нельзя добавить один и тот же тайтл в избранное дважды
}

model ReadingProgress {
  id            String   @id @default(uuid())
  userId        String
  mangaId       String   // id тайтла на MangaDex
  chapterId     String   // id главы на MangaDex
  chapterNumber Float    // чтобы не ходить в MangaDex за номером главы просто для списка
  pageNumber    Int      // текущая страница внутри главы
  updatedAt     DateTime @updatedAt // дата последнего чтения
  @@unique([userId, mangaId]) // одна запись прогресса на тайтл — последняя открытая страница
}
```

Полная версия с индексами/каскадным удалением — в
`server/prisma/schema.prisma`.

### API

Все эндпоинты — `http://localhost:4000/api/...` в разработке (порт и
адрес — в `server/.env`, `CORS_ORIGIN` разрешает запросы с
`http://localhost:5173`, где крутится фронтенд).

| Метод и путь | Что делает | Нужен токен? |
|---|---|---|
| `POST /api/auth/register` | Регистрация: имя + email + пароль (мин. 8 символов) → создаёт пользователя, хеширует пароль (bcrypt), возвращает JWT | Нет |
| `POST /api/auth/login` | Вход: email + пароль → проверяет хеш, возвращает JWT | Нет |
| `POST /api/auth/google` `{ credential }` | Вход/регистрация через Google — `credential` это ID-токен от Google Identity Services на фронтенде, сервер проверяет его подлинность и создаёт/находит пользователя по email | Нет |
| `GET /api/auth/me` | Данные текущего пользователя по токену | Да |
| `GET /api/favorites` | Список id тайтлов в избранном | Да |
| `POST /api/favorites` `{ mangaId }` | Добавить в избранное | Да |
| `DELETE /api/favorites/:mangaId` | Убрать из избранного | Да |
| `GET /api/progress` | Весь прогресс чтения пользователя | Да |
| `PUT /api/progress` `{ mangaId, chapterId, chapterNumber, pageNumber }` | Сохранить/обновить прогресс по тайтлу (upsert — одна запись на тайтл) | Да |
| `GET /api/admin/users?q=&sort=` | Список пользователей (имя/email/дата/способ входа) — см. "Админ-панель" ниже | Да, + `isAdmin=true` |

### Вход через Google (и почему пока не через Apple)

Кроме email+пароля, можно войти через Google — фронтенд использует
`@react-oauth/google` (официальный подход Google, называется "Google
Identity Services"): пользователь нажимает кнопку, Google возвращает
подписанный ID-токен с email/именем внутри, фронтенд просто пересылает
этот токен на `POST /api/auth/google`, а сервер проверяет его подлинность
через `google-auth-library` (официальная библиотека Google — проверяет
подпись сама, без похода в интернет за каждым запросом) и создаёт/находит
пользователя по email.

**Настройка (нужно один раз, бесплатно)**: зайти на
console.cloud.google.com → создать проект → APIs & Services →
Credentials → Create Credentials → OAuth client ID → Web application →
в Authorized JavaScript origins указать `http://localhost:5173` (и позже
домен продакшена) → скопировать Client ID (он не секретный, специального
"секрета" в этой схеме не нужно) → вписать в `server/.env`
(`GOOGLE_CLIENT_ID`) и в корневой `.env` фронтенда (`VITE_GOOGLE_CLIENT_ID`,
см. `.env.example` в обоих местах). Без этой переменной кнопка "Войти
через Google" просто нигде не появляется — не ломается, а честно
отсутствует (см. `src/config/google.ts`, тот же принцип, что и с
контактами в `src/config/contacts.ts`).

**Apple — пока только кнопка-заглушка** ("скоро", неактивна). "Sign in
with Apple" технически похож на Google, но требует платного членства в
Apple Developer Program (99$/год) для настройки Services ID и приватного
ключа — несоразмерная цена для тестирования MVP. Подключим, когда/если
дойдёт до реального релиза (см. ROADMAP.md).

### Админ-панель (`/admin`)

Простой список пользователей (имя, email, дата регистрации, способ
входа) для владельца проекта — не полноценная CMS, просто способ видеть,
кто регистрируется.

**Как устроена защита** — два независимых слоя, оба обязательны:

1. **На backend** (реальная защита, а не просто "спрятанная кнопка"):
   поле `User.isAdmin` (`Boolean @default(false)`) в
   `server/prisma/schema.prisma`. Роут `GET /api/admin/users`
   (`server/src/routes/admin.ts`) защищён двумя middleware подряд:
   `requireAuth` (проверяет JWT, как и остальные защищённые роуты) →
   `requireAdmin` (`server/src/middleware/admin.ts`, отдельным запросом
   к базе смотрит `isAdmin` пользователя из токена). Без валидного
   `isAdmin=true` в базе — `403`, даже если знать URL эндпоинта и
   подделать что угодно на фронтенде.
2. **На фронтенде** (`src/pages/Admin/Admin.tsx`) — только для UX: если
   `user.isAdmin` не `true` (значение приходит в ответе `/api/auth/me` и
   `/api/auth/login`/`/register`, см. `publicUser()` в `auth.ts`),
   страница сразу показывает "Access denied", не дожидаясь ответа
   backend. Это не замена серверной проверке — просто не показывать
   пустую попытку загрузки тому, кто и так не пройдёт.

**Как выдать себе доступ**: `isAdmin` **не выставляется через UI** —
специально, чтобы не было пути "зарегистрировался и сам себя назначил
админом". Проставляется вручную, напрямую в базе:

```sql
UPDATE users SET is_admin = true WHERE email = 'ваш-email@пример.com';
```

Выполнить это можно через Prisma Studio (`npx prisma studio` в
`server/`, если база локальная) или через `psql`/любой SQL-клиент,
подключённый к продовой базе на Render (адрес — в переменной
`DATABASE_URL` в Render Dashboard → Environment).

### Аутентификация: JWT в localStorage — и её цена

Пароли хранятся как **bcrypt-хеш**, не в открытом виде — если базу
данных когда-нибудь украдут, исходные пароли восстановить нельзя
(только перебором, что дорого и медленно). При входе сервер сравнивает
хеш введённого пароля с хешем в базе — сам пароль после регистрации
нигде повторно не хранится и не передаётся.

После входа сервер выдаёт **JWT-токен** — самодостаточную подписанную
строку с id пользователя внутри, срок жизни 30 дней. Фронтенд кладёт его
в `localStorage` (`mangared:token`) и добавляет в заголовок
`Authorization: Bearer <token>` к каждому запросу, требующему авторизации.
Плюс — сервер не хранит сессии, не нужно ничего чистить/масштабировать.

**Минус, о котором важно знать**: токен в `localStorage` доступен
любому JavaScript-коду на странице — если на сайт когда-нибудь попадёт
вредоносный скрипт (XSS), он сможет украсть токен. Более защищённый
вариант — `httpOnly`-cookie (обычному JS недоступна), но она требует
больше настройки (CORS с credentials, защита от CSRF) — сознательно
отложено, чтобы не удваивать сложность в момент первого знакомства с
аутентификацией. Если проект пойдёт в реальный прод с настоящими
пользователями — это первое, что стоит пересмотреть (см. ROADMAP.md).

### Гостевой режим: backend, только если пользователь вошёл

`src/services/favorites` и `src/services/progress` — теперь не просто
обёртки над localStorage, а обёртки, которые **сами решают**, куда
обращаться:

```ts
const token = getStoredToken() // localStorage.getItem('mangared:token')
if (token) {
  // авторизован — идём на backend (PostgreSQL)
} else {
  // гость — как и раньше, localStorage конкретного браузера
}
```

Компоненты (`TitlePage`, `Reader`, `Library`, `Favorites`, `History`)
вызывают одни и те же функции (`getFavoriteIds()`, `saveProgress()` и
т.д.) не зная, авторизован пользователь или нет — выбор источника
данных целиком внутри сервисов. Раньше (localStorage-only) эти функции
были синхронными, теперь — все асинхронные (`Promise`), даже для гостя:
единый контракт проще поддерживать, чем два разных API для двух режимов.

**Важно**: у гостя и авторизованного пользователя сейчас — **разные**
данные. Если гость добавил тайтл в избранное, а потом зарегистрировался,
старые гостевые данные из localStorage автоматически не переносятся в
базу — это в бэклог (см. ROADMAP.md).

### Почему прогресс хранит `pageNumber`, а не процент

В схеме БД сознательно нет поля "процент прочитанного" — только номер
страницы. Посчитать процент можно только зная общее число страниц в
главе, а мы намеренно нигде не храним метаданные MangaDex у себя (см.
"Источник контента" выше) — было бы дублированием данных, которые и так
живут на MangaDex. Поэтому UI-списки (Библиотека, История, "Последние
обновления") показывают "Глава N · стр. M" вместо прогресс-бара с
процентами — это честно отражает то, что мы реально знаем, не выдумывая
процент из воздуха.

## Слой доступа к данным (адаптер контента)

Ключевое архитектурное решение: компоненты **никогда** не обращаются к
MangaDex напрямую. Вместо этого — единый модуль-адаптер с функциями вида
`getPopularToday()`, `getTitleById(id)`, `getChapterPages(chapterId)`,
`getContinueReading()`. Раньше эти функции читали моки, теперь — реальный
MangaDex API через `src/api/mangadex`, но сигнатуры почти не изменились:
если источник контента снова сменится (см. "Открытые вопросы" в
DECISIONS.md), меняется только реализация внутри адаптера и мапперы,
компоненты не трогаются.

```
src/api/mangadex/       # сырой клиент MangaDex — ничего не знает про наши Title/Chapter
  client.ts             # fetch-обёртка, сборка query-строки
  constants.ts           # базовые URL, контент-рейтинг, язык контента
  types.ts               # сырые формы ответов API
  manga.ts, chapters.ts   # запросы: список/детали тайтла, теги, статистика, главы, страницы
  covers.ts               # сборка ссылок на обложки

src/services/content/    # адаптер — то, с чем работают компоненты
  index.ts                # публичный API адаптера
  mappers.ts               # MangaDex → наши Title/Chapter, резервные градиенты обложек
  types.ts                 # Title, Chapter, ReadingProgress
```

## Деплой

С 2026-07-29 проект готов к размещению на реальном хостинге — конфиги
в репозитории (`vercel.json`, `render.yaml`), сами аккаунты и нажатия
"Deploy" — шаг владельца проекта (см. "Ручные шаги" ниже, почему это
не может сделать ассистент).

**Адреса** (проверено вживую 2026-07-29 — регистрация, чтение, избранное
работают так же, как локально):

- Frontend (Vercel): https://mangared-theta.vercel.app
- Backend (Render): https://mangared-api.onrender.com

Бесплатный план Render "засыпает" backend после ~15 минут без запросов —
первый запрос после паузы может занять до ~50 секунд (сам под спит,
не ошибка). См. также запись в DECISIONS.md про перенос MangaDex-запросов
на прокси и `referrerPolicy="no-referrer"` для обложек/страниц — оба
фикса понадобились именно из-за поведения, которое проявляется только на
реальном хостинге, не в локальной разработке.

### Frontend — Vercel

Статический билд Vite (`npm run build` → папка `dist/`) плюс
`vercel.json` с rewrite-правилом `/(.*) → /index.html` — без него прямые
переходы на `/title/123` или обновление страницы (F5) на любом пути,
кроме `/`, отдавали бы 404, потому что `react-router` (client-side
роутинг) сам ничего не говорит серверу — все маршруты должны попадать в
один и тот же `index.html`, а дальше роутер уже разбирается в браузере.

Переменные окружения на Vercel (Project Settings → Environment
Variables):

| Переменная | Значение |
|---|---|
| `VITE_API_URL` | `https://<адрес backend на Render>/api` |
| `VITE_GOOGLE_CLIENT_ID` | (опционально, шаг 3 в ROADMAP.md — пока можно не задавать, кнопка "Войти через Google" просто не появится) |

### Backend + PostgreSQL — Render

`render.yaml` — это Blueprint: Render читает его из корня репозитория и
сам предлагает создать обе части (базу данных и веб-сервис) одним
нажатием, без ручной настройки каждого поля.

Переменные окружения, которые Render **попросит ввести вручную**
(помечены `sync: false` в `render.yaml` — специально не хранятся в
репозитории, так как это секреты):

| Переменная | Значение |
|---|---|
| `JWT_SECRET` | Длинная случайная строка (не пароль, который нужно запоминать — сгенерирована один раз и просто вставляется). Скомпрометированный `JWT_SECRET` = все выданные токены становятся подделываемыми, поэтому это не то же самое, что обычный пароль от аккаунта. |
| `GOOGLE_CLIENT_ID` | Оставить пустым до шага 3 из ROADMAP.md — без неё вход через Google просто не появится в интерфейсе, ничего не сломается |
| `CORS_ORIGIN` | URL фронтенда на Vercel, например `https://mangared.vercel.app` (без слэша на конце). Можно перечислить несколько через запятую — например, прод-домен и адрес превью-деплоя Vercel |
| `DATABASE_URL` | Заполняется автоматически Render (`fromDatabase` в `render.yaml`) — вводить вручную не нужно |

### Ручные шаги (может выполнить только владелец проекта)

Ассистент не может создавать аккаунты, проходить OAuth-авторизацию
GitHub/Google/Render/Vercel от чужого имени или подтверждать формы
где вводятся секреты — это относится к действиям, которые по
соображениям безопасности должен выполнять сам пользователь. Всё
остальное (код, конфиги, документация) уже готово, остаётся:

1. **Vercel**: зайти на vercel.com → войти через GitHub → "Add New
   Project" → выбрать репозиторий `Krrril/mangared` → Framework Preset
   определится как Vite автоматически → задать `VITE_API_URL` (см.
   таблицу выше, потребуется URL backend с Render — можно сначала
   задеплоить backend, потом frontend) → Deploy.
2. **Render**: зайти на render.com → войти через GitHub → "New" →
   "Blueprint" → выбрать тот же репозиторий → Render найдёт
   `render.yaml` и предложит создать `mangared-db` + `mangared-api` →
   при создании ввести `JWT_SECRET` и `CORS_ORIGIN` (см. таблицу выше)
   → Apply.
3. После того как оба адреса известны — если `CORS_ORIGIN` на Render
   задавался до появления реального адреса Vercel, обновить его в Render
   (Environment → отредактировать переменную → сервис передеплоится
   сам) и `VITE_API_URL` на Vercel аналогично, если backend
   передеплоился на новый адрес.
4. Вписать оба финальных адреса в раздел "Адреса после деплоя" выше.

## Почему не монорепо с React Native прямо сейчас

Мастер-план предполагает переиспользование логики в React Native. Делать
монорепо (Turborepo/Nx) с самого начала — преждевременно: пока нет второй
платформы, монорепо только добавляет сложность конфигурации без пользы.
Решение: с самого начала держать бизнес-логику (адаптер контента, работу с
прогрессом чтения, форматирование) в `src/services` и `src/utils` без
привязки к DOM/веб-специфичным API — это и есть подготовка к переносу,
без цены монорепо уже сейчас. Монорепо — рассматриваем как решение
момента, когда реально начнётся React Native (см. ROADMAP.md, v3+).
