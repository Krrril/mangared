- URL обложки для Telegram: `<SITE_URL>/covers/<mangaId>/<файл>.512.jpg` (SITE_URL из `telegramConfig().siteUrl`, по умолчанию https://www.mangagreen.com; прямых ссылок на uploads.mangadex.org больше нет). Имя файла проверяется по тому же белому списку, что и в `api/cover.ts`; нестандартное имя = тайтл без обложки.
- Перед отправкой сервер сам делает GET каждой обложки (по 3 одновременно, таймаут 20 с): 200, `image/jpeg`, ≤5 МБ. Именно GET с чтением тела до конца, а не HEAD: так обложка попадает в кэш Vercel (проверено на проде: HEAD по холодной обложке даёт MISS, после GET — HIT). Не прошедшие проверку исключаются из альбома, остальные идут как обычно.
- Формат: ≤4 тайтла в сообщении; ≥2 обложки = `sendMediaGroup`, подпись только у первой (≤1024, при нехватке места сначала убираются жанры, потом автор, потом тайтл переносится в следующее сообщение); 1 обложка = `sendPhoto` с той же подписью; 0 обложек = текст (лимит 4096). В конце «Источник: MangaDex».
- Если Telegram отверг альбом/фото (WEBPAGE_MEDIA_EMPTY, WEBPAGE_CURL_FAILED, «failed to get HTTP URL content»…), уходит тот же текст без картинок; причина пишется в `TelegramPost.error` (статус остаётся `sent`; в админке строка с красной причиной). Причины непрошедших проверку обложек тоже пишутся туда. Для тестовой подборки (без записи в БД) замечания возвращаются в поле `warnings` и показываются в сообщении админки.
- TELEGRAM_DIGEST_COVERS=false — поведение прежнее (только текст, лимит 4096, обложки не запрашиваются). Обложки Originals не тронуты (TELEGRAM_ORIGINALS_POSTS/COVERS остаются выключенными).
- **Фильтр безопасности подборки (в той же ветке, поверх обложек):** в подборку идёт только рейтинг `safe` и без тега doujinshi. Константы `DIGEST_ALLOWED_RATING` и `DIGEST_EXCLUDED_TAGS` (id тега doujinshi `b13b2a48-c720-44a9-9c77-39c9979373fb`, сверен с API MangaDex) в `telegramDigest.ts`. Фильтр и в запросе к MangaDex (`contentRating[]=safe`, `excludedTags[]=…&excludedTagsMode=OR`), и повторная проверка каждого тайтла (`safetyRejection`; рейтинг не указан = исключить). Если после фильтров тайтлов меньше 8 — подгружается следующая порция списка (по 40), не более 4 дозагрузок (итого ≤5 запросов списка). Статистика отбора (`DigestFilterStats`: просмотрено/исключено/в подборке/порций и причины doujinshi, suggestive, erotica, pornographic, прочий рейтинг, уже были, нет читаемой главы) возвращается в `runDigest().filter`, хранится в памяти процесса (после перезапуска сервера пусто, в БД не пишется) и показывается в админке: вкладка «Telegram» → «Последний отбор» (10 языков). ### Обложки MangaDex: причина и решение (work/covers-fix)
**Причина — НЕ 429 и не слабые повторы.** CDN обложек `uploads.mangadex.org` отвечает браузерам `403 text/plain «Bot challenge not passed, refresh this page.»` (воспроизведено в браузере на проде со всеми размерами .256/.512/оригинал, с любым referrer и CORS-запросом; из Node с честным User-Agent `MangaGreen/1.0` тот же файл отдаётся 200 — отличается только браузерный UA без пройденной проверки). Документация MangaDex (https://api.mangadex.org/docs/2-limitations/): «We will serve the wrong response for any image hotlinked from our domains», трафик к ним «MUST» идти через собственный прокси, User-Agent не подделывать, заголовок Via запрещён. То есть прямая подгрузка обложек в браузере с чужого сайта сейчас блокируется. Старый ImageWithRetry делал 3 попытки на каждую из ~24 обложек разом (72 запроса, все 403) и навсегда оставлял заглушку; «популярные грузятся» — вероятно из кэша браузера. Что сделано в ветке: очередь (≤6), запасные размеры, повторы с ростом паузы и Retry-After (читается одним GET-запросом без тела после первой неудачи), при 403 — сразу стоп и кнопка «Повторить» по тапу, предохранитель (после 4 подряд провалов на 90 с не ходим в сеть). Это НЕ возвращает обложки, пока MangaDex блокирует — оно лишь перестаёт долбить CDN и даёт кнопку.

**Что вернёт обложки — серверный прокси (НЕ реализовано, по вашему запрету; решение за вами).** Плюсы: единственный способ, который MangaDex прямо требует; сервер ходит с честным User-Agent и получает 200; можно кэшировать (Render стоит за Cloudflare: ответы с `Cache-Control: public, max-age=…` на путь вида `/api/cover/<id>/<file>.jpg` могут кэшироваться на краю по расширению .jpg, нагрузка на origin мала); не хранит копий (в отличие от R2). Минусы: трафик обложек идёт через наш Render (≈1 МБ на страницу каталога из 24 карточек; на бесплатном плане лимит исходящего трафика ~100 ГБ/мес); холодный старт Render снова задерживает картинки; нужны per-IP лимиты (есть в api-resilience) и белый список путей (только /covers/<uuid>/<file>) во избежание открытого прокси; юридически проксирование = передача чужих обложек пользователям, как и сейчас, но уже от нашего имени — условия MangaDex и права правообладателей тут надо учитывать так же, как при прямой подгрузке. Копирование в R2 хуже: хранение и раздача копий без разрешения, расхождение при смене обложки, прямое нарушение духа правил. Рекомендация: прокси с кэшем на краю + белый список, отдельной задачей после слияния; до тех пор в каталоге будет кнопка «Повторить».
